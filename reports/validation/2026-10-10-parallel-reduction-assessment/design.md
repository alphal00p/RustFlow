# Bounded ordered whole-unit batches

This is an isolated native API experiment. It changes neither a unit reduction's pending queue nor discovery, source admission, rule selection, arithmetic, terminal semantics, or final proof replay. No production change or speedup is established here.

The compile-time gate confirms that the native verified program, reductions, coefficient types, RustFlow wrapper/context, Symbolica Atom and RunContext implement Send + Sync. The existing memo intentionally holds its mutex through an entire miss. Calling the existing memo API on several threads would therefore serialize misses.

The proposed explicit `reduce_batch_memoized` borrows one immutable program. A coordinator holds the memo mutex; a private Rayon pool runs only the existing plain `reduce`. No worker accesses the cache. The coordinator performs cache lookup, recency changes, insertion and eviction in input order after workers finish. It snapshots only initial key presence, never decodes early. Initially absent duplicate keys share one planned job, but a later ordered cache miss executes again if the earlier result was uncacheable or has been evicted. An initially present key that is evicted before its turn is also reduced at that turn. With memo disabled, duplicate inputs execute independently.

The complete batch returns one ordered Result per input and is explicitly not fail-fast. Owned codec errors propagate for the affected item; no error is converted into a miss. Later items can already have executed when an earlier item fails. Statistics therefore separate returned logical applications, memoized logical applications, uncached returned applications, every known actual native application, unused prefetch work, and native errors whose partial application counts are unavailable. A false `actual_application_count_complete` forbids treating the known sum as the full actual work count. Codec errors do not erase known work. Existing frontend counters must keep their prior consumed-prefix meaning; new batch execution counters account for all work performed.

`max_workers` bounds private pool threads and `max_in_flight` bounds input/output window count. Per-unit application/pending limits are unchanged. These are structural count bounds, not total decoded coefficient memory, CAS scratch, elapsed-time, or coefficient-growth bounds. The encoded memo's separate retained payload caps remain unchanged. Pool construction happens before native work/cache mutation. Native unit calls still lack internal cancellation polling; a caller polls before and after each bounded batch.

At the RustFlow boundary, the first useful grouping is only the nonzero, ordered components inside one existing `active::reduce_sum`. Each derivative currently has at most the shifted-slot count of components. Validate inputs and returned labels, preserve ordered condition/weighted-coefficient aggregation, and preserve the original logical error prefix. Do not prefetch the evolving active pending frontier, reorder its visitation, change candidate budgets, or replace the mandatory final original-target and every-basis-derivative audits. Replaying the final native program remains mandatory.

The memo serializer inherits Symbolica process-global state export: partial export includes registered variable lists and finite fields. Plain native reduction here operates on existing rational-polynomial maps; ordered insertion performs Atom interning. Tests compare serial/batch cache bytes after common source construction. No byte-stability claim is made under unrelated concurrent process-global Symbolica registrations.

Review identified one additive frontend telemetry requirement: expose each ordered post-item memo-usage snapshot, rather than just final usage, so intermediate peaks and an early logical error's prefix can be represented exactly. The first isolated compile predates this addition and is retained separately. Revision 2 provides `memo_usage_after: Vec<Option<GuardedUnitMemoUsage>>` parallel to the ordered items, with a regression proving a real intermediate 2→1 retained-output peak. No production integration is implied by it.
